# 移动端「英文文献阅读 + 翻译 + AI 解读」竞品调研

调研时间：2026-11-20 ｜ 视角：为本地优先的 Windows 桌面论文库（Rust+SQLite / Electron+React+pdf.js / BabelDOC / rclone）规划 Android 端。

---

## 0. 结论速览

1. **没有「手机原生」的成熟产品**。小绿鲸只有 Pad 版，手机走微信公众号 H5；ReadPaper 只有 iPad；Zotero 有 iOS/Android 但纯管理、无翻译无 AI；Scholaread（靠岸）是少数真为手机做重排的。
2. **胜负手不是翻译引擎，而是三件基础设施**：PDF 本地渲染与状态保持、选区精度、阅读/批注跨端一致。小绿鲸 iPad 版仅 2.7/5（444 评分），差评几乎全集中在这三点。
3. **"原位版面翻译"在手机上只能当第二模式**；默认应是「单栏重排 + 逐段对照」或「云端双语 PDF 再读」。
4. **同步冲突全行业都没解决**：小绿鲸官方建议"不要多端同时读"，靠最后写入覆盖 + 手动恢复。这正是本地优先 + rclone 要自己补的一课。

## 1. 小绿鲸：产品画像与移动端取舍

### 1.1 平台矩阵（官方口径）

| 平台 | 状态 | 依据 |
|---|---|---|
| Web | 2021.08 上线 | 官网[发展历程](https://www.xljsci.com/about/) |
| Windows / macOS | 2021.09 上线；另有鸿蒙 PC 版、Microsoft Store 版 | 同上 |
| iPad / Android 平板 | 2023.11 上线 | 下载页标题即[「安卓 Pad 版」](https://www.xljsci.com/download/android)、[「iOS Pad 版」](https://www.xljsci.com/download/ios) |
| 手机原生 App | **无** | 官方 FAQ：手机端在"文献阅读公众号→联系我们→个人中心→我的文献"里读（[FAQ 4.2](https://www.xljsci.com/faq/)）；早期商店描述亦写"暂不支持手机端"（[AppRecs 镜像](https://apprecs.com/ios/6450911529/)） |

累计用户官方口径 400 万+（2026.04）；包体 87.7 MB，要求 iOS/iPadOS 15.1+。

### 1.2 Pad 端能做什么

- **阅读**：云端库内打开 PDF（Pad 只支持 PDF，不支持 CAJ）；原版版面 + 横屏左右分栏译文。
- **翻译**：划词（长按选中→翻译）、"全文对照翻译（1:1 还原排版）"、10 引擎可切、学科翻译（113 个一级学科）、截图翻译（有用户反馈 Pad 端不可用）。
- **AI**：文献速读（6 大要点+思维导图）、图表解读、边读边问（20+ 预设问题）、侧边栏"小鲸助手"（V3.0.4 起移入侧边栏）、参考文献/引证解读。
- **笔记**：高亮、文字批注、手写（后加）、笔记模板。
- **管理**：题录自动提取、影响因子/分区、10000+ 引文格式、无限层级文件夹、标签、Zotero 导入。
- **同步**：云盘（会员 30G/50G/年，单篇 ≤200MB），三端"实时互通"；最多 3 台设备，扫码登录 30 天过期。

### 1.3 移动端明确做的取舍（有官方自述）

官方 2023-11 发布文（[《但凡出了Pad端，也不至于出这档子事》](http://mp.weixin.qq.com/s?__biz=MzA3MjM1Njc0OQ==&mid=2247497741&idx=1&sn=1ec3ab960cf58a90f62cdc8f6247a443)）写得很直白：

> "起初我们希望将PC端所有功能复制到平板端，然而现实很骨感……不得不做出取舍，初代Pad版保留基础核心功能。"

短期取舍：初代只有**划词翻译 + 批注**，"手写笔记、全文翻译"列为"下一步目标"，**Pad 端不能导入文献**（须先在 PC/网页导入），且不进华为、小米商店。7 人团队做了 200 多天。

几处结构性取舍：

- **纯云端库，不碰本地文件系统**：没有"打开手机里的 PDF"，一切进出云盘，离线能力未承诺——决定它不可能本地优先。
- **付费点围绕"次数"**：[订阅协议](https://www.xljsci.com/sla/)规定全文翻译 30 次/月（鲸会员）/50 次/月（AI 会员），单篇 ≤200 页、仅英译中，**加密件、扫描件不能译，不支持图片/表格翻译**；截图翻译 300/500 次/月；翻译按字符、AI 按 Token、网盘按容量计费。
- **是否 WebView 壳**：官方未说明。评论"每次打开都要更新重复内容"、切后台文档被关闭，像"混合渲染 + 弱本地状态"，**属推测**。

**差评即需求清单**（[App Store 评论](https://apps.apple.com/cn/app/%E5%B0%8F%E7%BB%BF%E9%B2%B8%E8%8B%B1%E6%96%87%E6%96%87%E7%8C%AE%E9%98%85%E8%AF%BB%E5%99%A8-%E5%B9%B3%E6%9D%BF/id6450911529?see-all=reviews)）：

- "切后台再进来，文献已经被关闭了"→ 无阅读态持久化；
- "为什么一定要做成符合页面大小"→ 缩放下限锁在 fit-page；
- "横屏翻译在右边，左边看不了多少"→ 分栏挤压原文；
- "左右两列内容连在一起选择，根本用不了"→ 双栏选区串栏；
- 手写"写一个字笔就消失"、"不能撤回笔画"、"经常闪退"。

## 2. 移动端论文阅读的典型交互范式

| 维度 | 桌面惯性 | 移动端事实标准 | 证据 |
|---|---|---|---|
| 版面 | 双栏原版、双页对开 | **单栏重排/文本流**为默认，原版 PDF 为备选 | Scholaread 把"复杂双栏转成公众号排版"[官方帮助](https://www.scholaread.cn/help/baidu-scholaread)；秘塔"阅读模式"重渲染多列与图表混排[官方发布](http://mp.weixin.qq.com/s/U-Rv2UhsXdNWON-9bRhbXw)；知网研学走 XML 流式阅读 |
| 翻页 | 连续滚动 | 重排纵向连续滚动；原版模式横向翻页 | 同上 |
| 缩放 | 自由缩放 | 双指缩放，但常以 fit-page 为下限（小绿鲸差评） | App Store 评论 |
| 选择 | 鼠标拖选、双击词 | 长按→拖手柄→浮动/底部工具条（翻译/高亮/笔记/复制） | 小绿鲸"长按选中→点翻译"[官方教程](http://mp.weixin.qq.com/s?__biz=MzA4MDYzMDIxMA==&mid=2650117312&idx=1&sn=bfd459ebb6394c9077a78d926c521b7c) |
| 译文呈现 | 侧栏/悬浮 | 四选一：段后插入、右侧分栏、浮层气泡、整页替换/双语 PDF | Scholaread=逐段上下对照；小绿鲸=横屏分栏、竖屏浮层（"弹窗太大"）；BabelDOC/沉浸式翻译=双语 PDF |
| 笔记 | 键盘+手写 | 手写优先，键盘输入常被砍（评论在求"边栏打字笔记"） | 同上 |
| AI 面板 | 右侧常驻 | 底部抽屉 / 侧边栏 / 独立 Tab；Kimi 是纯聊天流 | 小绿鲸 V3.0.4 助手移入侧边栏 |

规律：**移动端"原版 PDF"必须保底存在**（图表/公式/核对不可替代），但它是"核对模式"，不是"阅读模式"。

## 3. 「原位版面翻译」的真实可行性

**桌面上已基本可行**：BabelDOC 用中间表示（IR）把版面与语义解耦，做术语抽取、跨页上下文、公式占位，再自适应回填排版（[ACL 2026 Demo](https://aclanthology.org/2026.acl-demo.25/)）。沉浸式翻译在移动端也能产出保留排版的双语 PDF（[官网](https://immersivetranslate.com/zh-Hans/)）。

**手机上三重硬约束**：

1. **可读性**：A4 双栏论文在 6 寸屏正文约 6–7pt；中文更宽，即使译文完美回填也塞不回原槽位。小绿鲸"1:1 还原排版"在 Pad 成立，在手机必然退化。
2. **算力/内存**：BabelDOC 依赖 Python + 版面模型 + 字体子集化，单篇数分钟、数百 MB 内存，端上跑不动。
3. **字体与增量**：回填需嵌中文字体子集，产物常大于原文；改一页要重排整份。

行业因此收敛到四条妥协：

- **A. 云端生成双语 PDF，手机只当阅读器**（沉浸式翻译、BabelDOC）——保真最高，代价是上传、延迟、隐私与配额。
- **B. 单栏重排 + 逐段对照**（Scholaread）——阅读体验最好，但已非"原版面"。
- **C. 重渲染成"阅读模式"**（秘塔）——牺牲版式换可读性。
- **D. 只做划词/截图**（小绿鲸初代 Pad）——成本最低，把"读整篇"的负担还给用户。

**判断**：手机端应把原位版面翻译定位成**可切换的第二阅读模式**（核对图表/公式），默认是"单栏文本流 + 段后译文"。云端翻译 + 端侧缓存（译文块、术语表、已译页）是成本与体验最优解；全端侧翻译仍不成立。

## 4. 同类产品的跨设备同步做法

| 产品 | 同步内容 | 冲突/一致性策略 |
|---|---|---|
| 小绿鲸 | 文献文件（云盘）、笔记、批注；阅读位置未见官方说明（**不确定**） | 官方 FAQ："不建议同时进行文献阅读，会造成笔记/批注被覆盖不能保存"，另有"备注恢复"[FAQ 4.1](https://www.xljsci.com/faq/) → last-write-wins + 事后恢复 |
| Zotero（iOS/Android 官方版） | 个人/群组库、元数据、笔记、PDF 批注（高亮/笔记/图片/墨迹）、附件 | 以 zotero.org 为准的客户端-服务器模型；官方功能表**未提阅读进度**[iOS 文档](https://www.zotero.org/support/ios) |
| ReadPaper | iPad/Win/Mac/Web 同步，支持离线浏览；手写/截图笔记 | 官方称"real-time synchronization"[App Store](https://apps.apple.com/au/app/readpaper/id1610085967) |
| Scholaread | 文献、笔记、"三端阅读进度保持一致" | 未公开冲突策略 |
| Readwise Reader | 高亮即时进 Readwise 库、多端阅读位置 | 官方文档：**"刷新"文章=删除重存，批注一并丢失**（[docs](https://docs.readwise.io/reader/docs/faqs/miscellaneous)）→ 文档 identity 必须稳定 |
| MarginNote 4 | 学习集/脑图/卡片，iCloud 同步 | 单用户单设备为主 |
| Scholarcy | 无移动 App（[第三方核实](https://www.positioniseverything.net/tools/scholarcy/)） | — |

三点经验：

1. **没人做真正的并发合并**，行业默认"单写者 + 云端为真"，代价是丢批注——对本地优先产品这是差异化机会。
2. **文档身份要稳定**（Readwise 的教训）：用内容哈希/DOI 做主键，避免"重存即失批注"。
3. **阅读位置是最便宜、感知最强的同步项**，比 AI 对话历史重要得多（后者几乎无人跨端同步）。

## 5. 对「桌面本地库 + Android 端」的建议

### 必须做（缺一个就不成立）

1. **本地渲染 PDF，不做 WebView 壳**。原生（PdfRenderer/MuPDF）或原生滚动的 pdf.js 容器；打开 <1s，切后台回来仍在原页。
2. **阅读位置三元组**：页码 + 页内偏移 + 缩放/模式，双向同步。
3. **批注走 op-log 而非整文件覆盖**：以 `(docHash, page, rect, id, updatedAt, deviceId)` 增量写入、服务端行级合并；否则重演小绿鲸"批注被覆盖"。
4. **默认单栏重排 + 段后译文**，一键切原版（图表/公式核对）；重排失败优雅降级到 fit-width。
5. **按需翻译 + 本地缓存**：只翻可视区段落，缓存译文块与术语表；离线可读原文与已缓存译文。
6. **把"选区"当第一优先级打磨**：跨栏选区、手柄可拖、长按不误触、缩放不锁 fit-page。小绿鲸 2.7 分主要败在这里。

### 应该砍（v1 不要碰）

- 完整文献管理（文件夹树、10000+ 引文格式、影响因子、批量标签）→ 手机只留"最近/收藏/搜索"。
- 手写/触控笔批注（工程量大、评价方差极大）。
- 端上全文翻译与版面回填、AI 综述/PPT/写作——桌面或服务端的事。

### 必须放服务端

- **翻译与 LLM 调用**：密钥不进客户端；配额、计费、缓存命中率都在服务端。
- **版面解析/重排（BabelDOC + 模型）**：手机 CPU/内存不可行，且需 Python 运行时。
- **同步中转**：rclone 只能搬文件，无法逐条合并与冲突检测。建议 `每设备 SQLite + 变更日志 → 服务端合并 → 下发`；rclone 只管 PDF 大文件冷备，别让 rclone 同步 SQLite。
- **OCR、元数据与影响因子查询**。

> 一句话收束：移动端不是缩小版桌面——它要独立的阅读态模型（重排/文本流/位置锚点）和独立的同步语义（增量、可合并）。这两件做对，翻译最容易追平。
