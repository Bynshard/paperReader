# 从预发布到日常可用：剩余工作与交付标准

更新日期：2026-11-01。代码基线：`744431d`。这是当前开发清单；早期设计、DS 任务和验收记录作为历史证据保留，遇到状态冲突以本文及更新的实际测试结果为准。

## 1. 当前判断

当前是有真实构建与测试支持的 Windows 预发布项目。论文管理、PDF 阅读、基础批注、离线 OCR 和 AI 调用框架已经存在；可以进入实际用户试用。完整的翻译安装体验、真实服务验证、长期任务与数据升级、万篇全文检索性能仍未闭环，尚不能直接作为用户唯一的主力论文库。

“真正可用”的目标是：普通 Windows 用户下载后能完成配置；已有论文安全迁入；每天导入、查找、阅读、翻译、问答与记笔记；关闭、重启、断网或升级后数据可恢复；出现故障时能理解并处理，而不需要开发者修改环境变量、修数据库或分析原始日志。

这里区分三种工作：**已有实现但待真实验收**、**现有实现仍有明确缺口**、**扩展功能**。没有证据的项目不能写成完成，已通过的功能也不必重做。

## 3. 发布前必须补齐的工作

优先级定义：P0 阻塞对应核心用途的日常交付；P1 影响长期管理和体验，进入随后一轮；P2 可选增强。P0 中的真实账号/旧库项需要可用的测试环境或用户参与，工程准备可以先完成。

### R01 · P0 · Windows 首次使用与翻译引擎安装

**现状：已有配置界面，安装与诊断闭环缺失。** 包内没有 BabelDOC/Python 运行时及其全部资源。用户仍需自己安装并找到可执行文件；保存 API 配置后需要重启，没有测试连接按钮。

落地工作：

- [ ] 建立首次使用流程：选择论文库、选择 API 或 Codex 问答、配置翻译引擎，逐项显示就绪状态。
- [ ] 复用 BabelDOC 官方发行方式或固定版本的独立环境，提供可管理的安装/定位流程；记录版本、校验和、资源准备结果，失败可重试。先完成可重复的 Windows 安装验证，再确定随包携带还是首次安装。
- [ ] 提供引擎检查、API 连接测试、模型可用性测试，区分未安装、认证失败、限流、网络超时、模型名错误及资源缺失。
- [ ] 需要付费的测试明确说明内容与用途；自动测试继续使用本地替身。
- [ ] 在用户未配置全文翻译时给出直达配置的入口；把 Codex 问答和 BabelDOC 全文翻译的配置分别说明。

**完成标准：** 在没有 Node/Rust/Python/Codex CLI 的干净 Windows 用户环境，从下载到第一份真实全文译文可按界面完成；无需手改环境变量。保存、退出、重开后配置有效；系统凭据服务不可用时有明确提示，已有 Key 不回显。

代码入口：`app/src/TranslationSettings.tsx`、`app/electron/translation-settings.cjs`、`app/electron/package.mjs`、`core/src/engine.rs`。

### R02 · P0 · 原位翻译质量与原文对照

**现状：真实译文存在，质量关口仍未全部通过。** 历史 M0 自动指标为覆盖率约 94.5%、起始位置偏差合格率约 85.5%，另有少量小于 8pt 的译文；公式、数字、语义和严重版面缺陷人工复核未完成。这是此前指定引擎/模型与样本的结果，不是新包当前服务的完整成绩。

落地工作：

- [ ] 重新冻结当前实际引擎、模型、参数、术语设置和输入 SHA256，使用当前 Windows 包完成真实输出。
- [ ] 完成现有 `review.csv` 人工审查；核心两篇每篇至少 6 页、至少 50 个语义片段、30 项公式/数值/单位检查，覆盖已知失败段落。
- [ ] 对双栏、长译文、图注、表格、算法块分别修复或给出可见回退，保留失败区域及原因。
- [ ] 阅读器明确当前同步是页码与页内相对位置同步；它还不是有验证的逐段映射。需要精确互跳时，持久化原文/译文区域映射及置信度，低置信时退回页定位。
- [ ] 纯扫描件在没有经验证的版式翻译管线前，清楚区分“OCR 后可阅读/选区翻译”和“输出保留版式的中文 PDF”。

**完成标准：** 按 [既有验证计划](VALIDATION.md) 的覆盖率、位置、字号、公式和语义门槛复核，不通过改分母或放宽阈值让测试变绿。任何关键数字、否定、公式或结论错误均需修复或明确标为未通过；失败任务保留原文。若声明精确段落互跳，再执行计划中的映射准确率与覆盖率验收。

代码入口：`core/src/engine.rs`、`app/src/Reader.tsx`；质量工具和证据：`moonlight/`、`artifacts/validation/m0-20261031T1005/`。

### R03 · P0 · 数据升级、自动备份与恢复

**现状：手动备份/恢复和事务已有测试，整个论文库的升级治理仍需补齐。** 当前以建表和逐字段检查追加列为主；已有同步结构版本，尚不能替代完整的库迁移台账、失败回滚与旧版本保护。

- [ ] 建立论文库 schema 版本、按序迁移、迁移前校验备份和失败恢复；旧程序遇到新库明确拒绝或只读打开，避免继续修改未知结构。
- [ ] 提供自动备份周期、保留策略、磁盘空间提示和最近成功记录；不把同一磁盘上的备份当作异地保护。
- [ ] 验证磁盘空间不足、目录只读、复制中断、强制结束进程、升级失败后的数据和附件一致性。
- [ ] 恢复后核对论文/目录/标签/笔记/批注/对话/译文及文件哈希，并验证下一次启动和同步行为。

**完成标准：** 至少覆盖当前两个历史发布状态到目标版本的升级测试；故障后用户可通过界面恢复到一致的新库，原库和已有文件不被破坏。诊断报告给出 schema、应用版本、错误阶段及恢复入口。

代码入口：`core/src/library.rs`、`core/src/organization.rs`、`core/src/backup.rs`、`app/src/BackupSettings.tsx`。

### R04 · P0 · 全文索引与长任务持久化

**现状：翻译已有持久状态和有界队列，异常退出后标记失败可重试；OCR/解析主要由阅读页面持有。** 手动停止能保留已写入页，重新发起可复用缓存，但它不是独立于界面、重启后继续的完整任务系统。导入和迁移也未统一到可恢复任务中心。

- [ ] 将 OCR/解析、批量导入、Zotero 迁移、备份与重建索引纳入持久任务记录，保存输入、文档版本、阶段和检查点。
- [ ] 支持安全取消、失败重试、页面关闭后继续或明确停止、重启后恢复待办；付费翻译重新发起前明确说明范围，不自动重复收费请求。
- [ ] 为每个文档维护“未索引/部分完成/完成/失败”，包括空白页、无文字页，提供全库索引检查与修复入口。
- [ ] 新设备同步完成后后台建立本地索引；不要求逐篇打开才可进行全文检索。
- [ ] 并发与内存有界，OCR 先逐页执行；导入和索引期间列表/阅读仍可操作。

**完成标准：** 任务中关闭论文、退出程序、强杀和重启均不丢已完成数据；能从检查点继续或明确重试。新设备同步后的库可检索已完成索引的所有论文，索引覆盖状态准确，失败条目可单独修复。

代码入口：`app/src/DocumentParsing.tsx`、`app/src/ocr.ts`、`app/src/TaskCenter.tsx`、`core/src/main.rs`、`core/src/library.rs`、`core/src/sync.rs`。

### R05 · P0 · 万篇库搜索与 Windows 性能

**现状：高命中率全文检索明确超标。** 最近两轮 P95 约 361ms / 491ms，目标为 200ms；短查询也存在数百毫秒延迟。列表与渲染通过，不能抵消这个结果。

- [ ] 分别测量查询、正文匹配归并、总数统计、排序分页、IPC 与界面防抖，保留 SQL 查询计划和原始样本。
- [ ] 优化大量正文块归并到论文的成本，优先复用 SQLite FTS 与现有开源组件；任何按论文聚合索引方案先验证更新/删除、短词、中文和磁盘成本。
- [ ] 验证连续快速输入时的过期结果处理、取消或限流，避免堆积无用重查询。
- [ ] 在目标 Windows 用户配置上跑实际万篇导入/迁移、索引、搜索、排序、导入竞争负载、阅读和 OCR；冷启动、首次升级重建、暖缓存分别报告。
- [ ] 保存可复现基线和版本对比，性能不达标返回失败，不能仅保留 JSON 却让 CI 忽略结果。

**完成标准：** 万篇场景按原预算验收：核心常用列表/排序/详情 P95 ≤100ms，高命中及稀有词正文搜索 P95 ≤200ms；界面首屏 ≤2s、排序显示 ≤200ms、普通 PDF 绘制 ≤3s。记录实际目标硬件，不能用 Linux 暖缓存结果替代 Windows 成绩。

代码入口：`core/src/search.rs`、`scripts/benchmark_library.py`、`app/e2e/benchmark.mjs`。

**当前不需要先重写 PDF 渲染器。** PDF.js 已有绘制和画布边界实测；现有瓶颈证据首先指向全文查询。原生渲染替换应由真实 PDF 性能问题驱动。

### R06 · P0 · 实际 AI 服务和账号使用闭环

**现状：协议实现与替身覆盖充分，当前 Windows 包的真实账号链路仍待验收。** API 配置已存在；Codex 整篇版式翻译尚未接入，账号登录不能替代 BabelDOC API 配置。

- [ ] 在目标 Windows 用户环境做全新浏览器登录、取消/重登、退出、过期后刷新、重启后状态恢复及限额错误验收。
- [ ] 通过实际软件完成“解析论文 → 查看上下文 → 真实提问 → 来源跳转 → 保存笔记 → 重启读取”。使用有权发送的公开或自有样本，记录服务与模型，不记录 token/Key。
- [ ] 对实际计划使用的 OpenAI 兼容端点验证地址/模型/超时/限流/错误；只列入已实测的兼容清单。
- [ ] API 和 Codex 两种问答模式的历史、流式输出、停止行为分别说明并补齐。当前 API 路径直接等待 RPC，不能把 Codex 的取消/流式能力视为两者已一致。
- [ ] 提供可判断原因的错误与恢复操作；不静默切换付费服务。

**完成标准：** Windows 上真实登录到论文问答的整个链路有记录；取消不保存半成品，服务故障不覆盖笔记，界面和真实请求的上下文一致。额度信息按服务返回展示，不承诺固定用量。

代码入口：`app/electron/codex-client.cjs`、`app/electron/ai-service.cjs`、`app/src/AiSettings.tsx`、`app/src/Reader.tsx`、`core/src/ai.rs`。

### R07 · P0 · AI 证据质量与长文预算

**现状：页尾检索遗漏已修复；仍以关键词、相邻片段、无匹配取样为主。** 32,000 字正文和有界历史不等于 token 预算；跨语言问题、整篇结论和图表问题仍可能缺少相关证据。

- [ ] 冻结问答评测集：至少 15 个有明确原文依据的问题和 5 个无依据问题，覆盖双栏、长文、扫描件、表格数值和附录。
- [ ] 分开评估证据召回、引用位置、回答正确性、拒答/不足提示；检索不到与模型答错分开记录。
- [ ] 按所选模型提供总请求预算：系统指令、元数据、问题、历史、正文和预留输出共同计入；准确计数或保守估算要明确区分。
- [ ] 改善跨语言召回和长文覆盖，先比较已有全文检索与开源检索组合；是否加入本地 embedding/重排由评测结果决定，不预设额外重型服务。
- [ ] 将图表、公式结构和低置信 OCR 明确标为能力边界。引入多模态时另做页面/区域和成本验证。

**完成标准：** 有编号答案和可定位证据的逐题报告；无依据问题不伪造出处，超预算和索引不全可见。评测不能用固定回答的模拟模型证明正确率。

### R08 · P0（迁移/云同步交付）· Zotero 和真实服务接管

**现状：功能已实现，用户真实库与真实供应商链路缺少证据。** 用户当前没有可提供的旧库，这项不是已经失败，也不能视为无缝迁移已确认。

- [ ] 用可取得并获准使用的真实 Zotero 库或匿名副本验收，核对层级目录、多 PDF、笔记、批注、网页快照、外链、缺附件和重复迁移；报告不支持/未迁移字段及原因。
- [ ] 提供迁入前预检、空间估计、迁移报告、错误条目重试；保留原 Zotero 库，验证迁入文件独立可用。
- [ ] 坚果云、七牛、OSS 各做至少一次真实双端往返：新增、编辑、删除冲突、断网、限流、重启后重试、凭据持久化。
- [ ] 做实际万篇初次同步、新设备接入和增量同步，记录总耗时、请求数、流量、临时空间；验证远端目录/对象规模和长期历史增长。
- [ ] 明确同步协议/库版本兼容策略，防止旧客户端修改新字段；计划快照/历史压缩与可证明安全的对象回收。
- [ ] 验证新设备的索引重建（依赖 R04）；明确 OCR 缓存、阅读位置、个人列配置各自是否同步。目前 OCR/FTS 属本地派生数据，阅读位置和列设置主要保存在本机 localStorage。

**完成标准：** 迁移逐项核对且可重复；每个声称可用的真实供应商有往返记录；冲突保留两端内容、损坏附件不入库、新设备能恢复全文搜索。Zotero 迁移并不等同于 Zotero 双向同步。

代码入口：`core/src/zotero_local.rs`、`core/src/sync.rs`、`core/src/sync_model.rs`、`core/src/sync_transport.rs`、`app/electron/sync-settings.cjs`。

## 5. 推荐执行顺序

### 第一批：让一台 Windows 机器形成真实闭环

1. R01：干净环境安装引擎、首次配置与诊断。
2. R02：用当前包跑真实全文译文，完成已有人工质量审查。
3. R06：实际网页登录和论文问答；记录 API 与 Codex 两种路径。
4. R03：库版本治理和升级前备份，保证后续改动可恢复。

交付物：当前 Windows 包、首次使用说明、真实译文/截图、逐项质量表、真实问答和备份恢复报告。只完成界面按钮或模拟测试不能关闭这一批。

### 第二批：满足大量论文的持续使用

R04 与 R05：任务/索引持久化、同步后重建、全文查询优化，再跑目标 Windows 万篇与大 PDF 压力测试。同步补齐 R09 的版本/旧批注可访问性，避免用户持续积累数据后难以回看。

交付物：可恢复任务、清晰索引状态、故障记录、原始时延/内存数据、与固定基线的对比。保留未达标项。

### 第三批：接管旧库并跨设备使用

R08 的真实 Zotero/云端验收，R12/R13 的元数据与引用量工作，R15/R16 的正式分发与持续回归。R08 可以在取得测试环境后提前并行准备；未取得真实库时保留“待环境”，不改成通过。

交付物：迁移核对表、真实双端同步报告、Windows 回归报告、准确的新版本 Release 与已知问题。

## 6. 何时可以说“日常可用”

下面是本项目的提议验收关口，尚未执行或通过的保持未勾选。

- [ ] 干净 Windows 环境无需开发工具完成下载、配置、导入、真实整篇翻译、对照阅读、真实 AI 问答、批注/速记保存与重启恢复。
- [ ] 原位翻译达到既有质量门槛，已知失败有明确提示，扫描/公式/图表能力边界准确。
- [ ] 数据升级有可恢复备份，失败不会破坏旧库；真实恢复能继续阅读、编辑与同步。
- [ ] 导入、索引/OCR 与翻译长任务可追踪、可取消、可恢复或明确重试，不静默丢进度或重复收费。
- [ ] 目标 Windows 上的万篇核心性能预算通过，且并发导入、索引时仍能阅读；大 PDF 峰值内存与释放有数据。
- [ ] 真实 Zotero 迁移核对完成；用户所用云服务至少完成实际双端往返，新设备可搜索已同步正文。
- [ ] 目标用户至少连续使用 7 天，每天执行导入/搜索/阅读/批注或速记，包含 20 次正常重启与受控故障，记录阻塞问题、耗时和内存。零已知数据丢失问题，阻塞项全部关闭。此项是拟定试用计划，不是已完成成绩。
- [ ] Release、功能说明、兼容范围和验收报告对齐同一提交；新包在源码目录外通过 CI，并有目标 Windows 桌面实测。

可以先交付“单机可用测试版”，再开放“旧库接管与多端同步”承诺；达到用户要求的完整项目，需要把以上相关关口全部补齐。

## 7. 任务交付格式

每个 R 编号可以直接作为独立开发任务。交付必须包含：对应问题与代码改动、复用组件/版本、数据兼容与恢复方式、实际执行命令、测试环境和输入、通过/失败/未运行结果、原始证据位置、剩余限制。需要账号、联网或真实旧库的任务，先完成可本地复现的准备，再把缺少的具体环境列出来。

工作原则：保留现有 Rust/SQLite、PDF.js、TanStack、Tesseract、BabelDOC、rclone 和官方 App Server 的已验证能力；优先修闭环与证据缺口。新依赖和架构调整都先用目标场景验证，不通过引入更多组件代替验收。
